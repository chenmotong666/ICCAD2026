ICCAD Contest Problem A - LLM-Assisted Netlist Exploration and Transformation Chung-Han Chou, Hung-Chun Chiu, Chih-Jen (Jacky) Hsu, and Yong Liu Cadence Design Systems, Inc.    • 2026.02.10    First Version    1. Introduction Recent advances in large language models (LLMs) have enabled users to interact with complex software systems through natural language instead of low-level commands or scripting interfaces. This change is particularly attractive for electronic design automation (EDA), where existing tool flows are powerful but often difficult to access for non-expert users due to their large command sets, intricate semantics, and long multi-step flows. In current practice, users must know exactly which tool to use, which command to call, what arguments to provide, and how to decompose a task into valid sequences of commands. While LLMs can accelerate coding and scripting, they usually have no built-in knowledge of a specific EDA tool’s interface or semantics. As a result, the main bottleneck shifts from writing code to specifying what the system should do, which operations are allowed, and how to verify that the result is correct. Natural-language instructions are often ambiguous and underspecified, and many EDA tasks require several tightly coupled steps such as analysis, transformation, and verification. Unlike casual applications, EDA flows also demand deterministic and verifiable behavior. In this contest, contestants are asked to build a system that accepts natural-language requests, interprets them, and executes the corresponding analysis or transformation flow on a gate-level Verilog design by means of a self-specified EDA engine. Each team must define its own logic-level EDA interface, implement it, and then drive this engine with an LLM-based agent that translates natural-language requests into sequences of EDA operations. The problem evaluates how well contestants can combine such an agent with netlist-level EDA tools while preserving the determinism, robustness, and correctness that EDA applications require. A long-term vision behind this problem is that one day a researcher or architect with a new design idea will no longer need to rely on experienced engineers (or students) to script and operate EDA tools by hand. Instead, the researcher would describe the intended architecture and constraints in natural language, and an AI agent would be able to translate these high-level intentions into concrete EDA workflows, invoke the appropriate tools, refine the implementation, and validate the results end to end. Achieving such a fully

Background and Related Work   Large language models are increasingly used to generate code, scripts, and configurations from natural-language descriptions, and many recent systems apply this capability to domain-specific workflows. However, directly applying such techniques to EDA raises several challenges. These program-synthesis-style approaches have important limitations in the EDA setting. A generated script can be syntactically valid but semantically wrong, for example by calling commands in an incorrect order or by applying transformations that violate timing or functionality. Typical program synthesis tasks also do not have a rich notion of persistent design state. They often treat each generation independently rather than as part of a multi-turn interaction on a single evolving netlist. Finally, such systems rarely integrate formal verification into the loop, which is crucial for reasoning about circuit correctness. In recent years, several studies have begun to explore LLM usage in EDA and hardware design. Xu et al. [4], for example, discussed opportunities and challenges of using large language models for hardware design tasks such as HDL generation. Other works investigate how LLMs can generate or refactor Verilog, explain verification logs, suggest assertions, or assist in documentation and design-space exploration. These early results 

=== PAGE 3 ===
suggest that LLMs can understand basic hardware descriptions and provide helpful guidance, but they also highlight robustness and correctness concerns. Most existing LLM-for-EDA applications focus on side tasks such as documentation, code completion, or informal assistance, rather than placing the LLM directly in the execution loop of netlist analysis and transformation. There is limited prior work where an LLM receives natural-language queries like “Does every path from A to B pass through C?” or transformation requests such as “Insert AND gates before all buffers with certain naming patterns,” and then orchestrates actual netlist modifications and formal checks. There is a broader line of research on safe or constraint-aware AI agents. Wu et al. [5] discussed how to incorporate formal constraints into the decisions of AI agents, and how to describe tools in terms of preconditions and effects. Verification-in-the-loop methods further suggest that agents can call formal or semi-formal verification tools to validate intermediate results and plans. These directions are highly relevant to EDA, where tasks depend on path properties, timing or depth bounds, and functional equivalence constraints. In summary, prior work shows that LLMs can plan multi-step workflows, call tools, and generate code or scripts. Initial LLM applications in EDA also show promise for assistance with hardware design and verification. However, there is still a gap between these demonstrations and a robust, correctness-centric system that can receive natural-language requests, transform gate-level netlists accordingly, and verify that all requested constraints are satisfied. Problem A is designed to bridge part of this gap by requiring contestants to build an LLM-assisted netlist exploration and transformation system that operates under realistic timing and correctness constraints.   3. Problem Formulation and Input Output Format This section defines the input, output, and requirements of this contest. 3.1 Program requirement The target framework conceptually contains two main components (although contestants are not required to follow any specific implementation style): an EDA tool back-end and an AI agent front-end. Contestants should first define a clear specification for the available EDA operations and implement an EDA tool (or tool interface) that follows this specification. The AI agent then receives natural-language requests, translates them into a sequence of EDA operations according to the specification, executes these operations on the current design, and finally produces the corresponding analysis results or transformed netlists. For each testcase, the system receives a gate-level Verilog design and a sequence of natural-language requests. In addition, a configuration for connecting to the LLM service

is supplied by the evaluation environment. The detailed format and usage of this LLM configuration are described later in Section 6.2. The system must load the design, process the sequence of requests, and produce a final output that satisfies all specified analysis and transformation requirements. The system is expected to interact with an external LLM service through a standard API in the contest environment. Contestants should connect to a cloud-based LLM endpoint (for example, a mid-sized model such as GPT-4o mini or a similar service). The LLM is used to interpret natural-language requests and to help plan the corresponding EDA flows. The LLM itself does not know the contest commands or tools in advance, so the system must describe its internal EDA interface to the LLM (for example, via prompt descriptions or schemas) and interpret the LLM’s responses back into concrete operations on the netlist. At a minimum, the system must support the following capabilities: 1. read a gate-level Verilog design into an internal representation. For every testcase, the system must write all its natural-language responses, in order, into a log file named <case_name>.log. Each response must be clearly delimited by a pair of tags: • A response header tag: #RESPONSE <id> where <id> is a monotonically increasing integer starting from 1 within that testcase (for example, #RESPONSE 1, #RESPONSE 2, and so on). This tag, and the line(s) that follow it, are treated as the system’s answer to the corresponding natural-language request. The beginning-of-testcase statement should also be recorded as response 1.

Task Specification This section describes the main types of tasks that will appear in the testcases. The example requests illustrate typical patterns; the actual benchmarks may vary in signal names, file names, detailed constraints, and structures. 4.1 Basic Operations The system must support reading a Verilog design and writing the final design to a Verilog file. These operations are the foundation for all other tasks. Example requests: “Load test1.v from the directory design/.” => LLM should call read design function  “Read in design from top.v.”  => LLM should call read design function “Output the design as top.v.”  => LLM should call write design function “Write out the current design to case28_out.v.” => LLM should call write design function

The system must treat these as instructions to update its internal design state (on load) or to generate the required output netlist (on write). In addition, the system must support setting the testcase name and starting the log for that testcase. At the beginning of each testcase, a request in natural language will indicate the testcase name and the desired log file name. The system must then save all its responses (which are printed to stdout) as a copy in the corresponding <case_name>.log file. Example request: “This is the beginning of testcase case23. Please output a copy of the log into case23.log.”  4.2 Analysis Tasks The contest will include analysis tasks where the system must answer questions about the structure or functionality of the current netlist. These tasks may involve path properties, signal relationships, or cone-level behavior, and typically require some form of graph traversal or formal reasoning. Example requests:  “Does every path from A to B pass through C?” “Find a path from input x to output y that does not pass through node n3.” “Do there exist signals a and b such that (a & b) is equivalent to z?” “What is the maximum logic depth from input in0 to output out3?” “Report all primary outputs whose logic cone contains more than 100 gates.” “Does dff1 and dff2 under the same clock domain?” “For output done, verify that it is asserted only when both req is 1 and busy is 0, and provide a counterexample if this is not true.”  For each such request, the system must interpret the question, perform the necessary analysis on the current netlist, and return a clear, concise answer. When applicable, the answer should include supporting information such as a counterexample path, a list of signals, or the measured depth value. 4.3 Transformation and Optimization Tasks The contest will also include transformation and optimization tasks where the system must modify the netlist and then verify that certain properties hold for the modified design. These tasks often require both structural edits and post-edit checks, such as equivalence or depth verification. Example requests:  “Add buffers to balance the depth from A to {B, C, D, E, F, G} with minimal buffer insertion.” “Insert buffer stages on high-fanout net clk_en so that no gate has fanout greater than 8, preserving functionality.” “Insert an AND gate before all buffers whose name includes _gc__, and connect the other input to _gc_ctrl.” “Optimize the logic cone of h so that the maximum depth is ≤ 5, and minimize the gate count.” “Reduce the number of gates in the logic cone of out0 without changing its functionality.”

“Remove any dangling gates and nets that do not affect any primary output.” “Replace all inverters followed by buffers with a single inverter, if this does not change functionality.” “Replace all 2-input OR gates in the cone of flag with equivalent logic built only from NAND and NOT gates.”  4.4 Combination of Tasks in a Testcase A simple testcase may include a single reading request, one analysis or transformation task, and a final writing request. A more complex testcase may contain multiple descriptions that request a mix of analysis tasks and a sequence of transformations and optimizations. The system must interpret and execute all requests in order. Each new request must operate on the current design state, which already includes all modifications made by previous requests in the same testcase. Netlist modification questions All hard requirements in the request must be satisfied, for example: • no unintended functional change. • structural bounds such as “maximum fanout ≤ 5” or “maximum depth ≤ 5”. If any hard requirement is violated, the testcase gets no credit.  Optimization questions Only solutions that satisfy all hard requirements are considered.
